================================================================================
แผนการดำเนินงานและขอบเขตโครงการ (Project Plan & Scope of Work)
โครงการ: Smart Gate Pass AI — ระบบขออนุญาตออกนอกสถานศึกษาผ่านแชทเว็บแอป (PWA)
         พร้อมระบบเปิดไม้กั้นอัตโนมัติด้วย AI จดจำใบหน้าและ IoT
สถานศึกษา: วิทยาลัยการอาชีพองครักษ์ (OICEC)
================================================================================

1. ข้อมูลภาพรวมโครงการ (Project Overview)
--------------------------------------------------------------------------------
- ชื่อโครงงาน (ภาษาไทย): ระบบขออนุญาตออกนอกสถานศึกษาผ่านแชทและสั่งเปิดไม้กั้นอัตโนมัติด้วยเทคโนโลยีปัญญาประดิษฐ์จดจำใบหน้า
- ชื่อแอปพลิเคชัน / ระบบ (ภาษาอังกฤษ): Smart Gate Pass AI
- ประเภทโครงงาน: ประเภทสิ่งประดิษฐ์ — ประเภทที่ 2 สิ่งประดิษฐ์ด้านนวัตกรรมและเทคโนโลยีดิจิทัล ปัญญาประดิษฐ์
- ชื่อสถานศึกษา: วิทยาลัยการอาชีพองครักษ์ (OICEC) — งานปกครอง วก.องครักษ์
- คณะผู้จัดทำโครงงาน (ระดับชั้น ปวส. ปีที่ 2 กลุ่ม 1 สาขาวิชาพาณิชยกรรม สาขางานเทคโนโลยีธุรกิจดิจิทัล):
  1) นายอัครชา เปมะวิภาต (หัวหน้าคณะผู้จัดทำโครงงาน)
  2) นายนัฐพล โหยหวล
- คณะครูที่ปรึกษาและผู้บริหารสถานศึกษา:
  * ครูผู้สอนและครูที่ปรึกษาโครงงาน: ครูอรรถเมธ ตะโกนา
  * ครูที่ปรึกษาร่วม: ครูธนพิสิษฐ์ ทาพา
  * หัวหน้าแผนกวิชาเทคโนโลยีธุรกิจดิจิทัล: ครูพัฒนา กลมพันธ์
  * รองผู้อำนวยการฝ่ายวิชาการ: นายชัยยศ มีสวัสดิ์
  * ผู้อำนวยการวิทยาลัยการอาชีพองครักษ์: นายประเสริฐ ถึงวิสัย
- รูปแบบโครงการ: โปรเจกต์จบ / ต้นแบบ (Prototype & Demo) ทำงานครบทุกฟังก์ชันร่วมกับชุดจำลองไม้กั้นขนาดฐาน 60 x 60 x 10 เซนติเมตร (ระยะเวลาดำเนินงาน: ภาคเรียนที่ 2 ปีการศึกษา 2569)
- ขอบเขตข้อมูลนำร่อง (Pilot Scope): แผนกวิชาเทคโนโลยีธุรกิจดิจิทัล ครบทั้ง 5 ชั้นปี (ปวช.1, ปวช.2, ปวช.3, ปวส.1, ปวส.2) ตามตารางสอนจริงภาคเรียนที่ 2/2569
- กล้องจุดสแกนใบหน้าหลัก: กล้องเว็บแคม USB Full HD (IOT/images.jpg) เชื่อมต่อโดยตรงกับเครื่องคอมพิวเตอร์/โน้ตบุ๊ก ใช้งานได้ครบทั้งลงทะเบียนใบหน้า เข้าสู่ระบบ Face ID และสแกนเปิดไม้กั้นอัตโนมัติ
- เลขที่ใบอนุญาตมาตรฐาน: รูปแบบ #GP-2569-XXX (เช่น #GP-2569-084)
- การเตรียมข้อมูลตั้งต้น (Pre-populated Master Data): บรรจุข้อมูลจริงครบทุกส่วน ได้แก่ ตารางเรียนทั้ง 5 ชั้นปี, รายชื่อครูประจำวิชา, ครูที่ปรึกษาตามคาบ HR, หัวหน้าแผนกวิชาฯ, งานปกครอง และผู้บริหาร เพื่อใช้งานได้ทันที
- ช่องทางผู้ใช้งานหลัก: Custom Web App (PWA - Progressive Web App) รูปแบบ Chat & Pass Dashboard พร้อมระบบแจ้งเตือน
- กระบวนการอนุมัติ: ระบบอนุมัติ 5 ขั้นตอนตามสายบังคับบัญชา (ครูรายวิชา -> ครูที่ปรึกษา -> หัวหน้าแผนก -> งานปกครอง -> รองผู้อำนวยการ)
- รูปแบบสถาปัตยกรรม: Hybrid Architecture (Cloud/Main Web Backend + Local Edge AI & IoT Gate Controller ภายในวง LAN)
- วัตถุประสงค์หลัก:
  1. ยกระดับการขออนุญาตออกนอกสถานศึกษาให้เป็นระบบดิจิทัล ตรวจสอบย้อนหลังได้
  2. คัดกรองและควบคุมการเข้า-ออกหน้าประตูอัตโนมัติด้วยเทคโนโลยีจดจำใบหน้า (Face Recognition) ผ่านกล้องเว็บแคม
  3. ป้องกันการสวมรอยและเพิ่มความรวดเร็ว ความเสถียรหน้าประตู แม้กรณีอินเทอร์เน็ตภายนอกขัดข้อง
  4. ตรวจสอบการเดินทางถึงสถานที่ปลายทางจริงและการกลับเข้าสถานศึกษาด้วยพิกัด GPS (Web Geolocation API & Geofencing) ภายใต้มาตรฐานการขอความยินยอมคุ้มครองข้อมูลส่วนบุคคล (PDPA Consent ทั้งข้อมูลชีวมิติใบหน้า AI และพิกัดตำแหน่งเฉพาะช่วงเวลาที่ขออนุญาต)


2. สถาปัตยกรรมระบบ 4 ส่วนหลัก (System Architecture)
--------------------------------------------------------------------------------
[2.1] ส่วนที่ 1: Client Layer (PWA Web App)
  - รองรับการติดตั้งบนสมาร์ตโฟน (Add to Home Screen) ทั้งสำหรับนักเรียน, ครู, ผู้บริหาร และ รปภ.
  - ระบบแจ้งเตือนแบบ Real-time (Web Push Notification / LINE แจ้งผู้ปกครอง / Webhook)
  - หน้าจอหลัก:
    * นักเรียน: ยื่นคำร้องผ่านแชท AI / ปุ่มลัดด่วน, ลงทะเบียนใบหน้า และติดตามบัตรผ่าน ACTIVE PASS
    * ผู้อนุมัติ 5 ระดับ: หน้าคิวงานรอตรวจสอบและลงนามอนุมัติ/ไม่อนุมัติ
    * รปภ./เจ้าหน้าที่หน้าประตู: หน้าจอมอนิเตอร์ตรวจสอบการผ่านเข้า-ออกแบบ Real-time

[2.2] ส่วนที่ 2: Web Backend & Database Layer (Cloud or Main Server)
  - Workflow Engine: ควบคุมลำดับขั้นการอนุมัติ 5 ระดับ (State Machine)
  - RBAC (Role-Based Access Control): จัดการสิทธิ์การเข้าถึงตามตำแหน่งงาน
  - User & Face Profile Database: จัดเก็บประวัตินักเรียน ข้อมูลตารางสอนตั้งต้น และ Face Feature Vectors (Embeddings)
  - Whitelist Sync Service: ส่งรายชื่อนักเรียนที่ได้รับอนุมัติครบ 5 ขั้นตอนและอยู่ในช่วงเวลาไปยังเครื่อง Local Edge ที่ป้อมยามประตู 1

[2.3] ส่วนที่ 3: Local Edge & AI System (ป้อมยามประตู 1 / คอมพิวเตอร์ตั้งโต๊ะหรือโน้ตบุ๊ก)
  - กล้องเว็บแคม (USB Webcam / Built-in Webcam): เชื่อมต่อโดยตรงกับเครื่อง Local Server / คอมพิวเตอร์ที่จุดสแกนป้อมยามประตู 1 ไม่ต้องตั้งค่าระบบกล้องวงจรปิด RTSP
  - รองรับการเปิดกล้องผ่าน WebRTC (getUserMedia) บนหน้าเว็บ PWA และ/หรือ OpenCV (cv2.VideoCapture(0)) เพื่อใช้เว็บแคมตัวเดียวได้ครบทั้ง 3 ฟังก์ชัน:
    1) ลงทะเบียนใบหน้า (Face Enrollment)
    2) สแกนใบหน้าเข้าสู่ระบบ (Face ID Login)
    3) สแกนใบหน้าสั่งเปิดไม้กั้นอัตโนมัติ (Gate Pass Face Scan)
  - Local PC / Laptop Server: ประมวลผล AI Face Recognition (เช่น InsightFace / FaceNet) ภายในเครื่องและวง LAN
  - Local Whitelist Cache: แคชฐานข้อมูลใบหน้าเฉพาะผู้ที่ได้รับอนุญาตในวัน/เวลาดังกล่าว เพื่อประมวลผลได้รวดเร็ว (< 0.5 - 1 วินาที) และทำงานได้แม้เน็ตภายนอกหลุด

[2.4] ส่วนที่ 4: Hardware & IoT Barrier Gate (ชุดจำลอง Prototype ขนาดฐาน 60 x 60 x 10 ซม.)
  - บอร์ดไมโครคอนโทรลเลอร์: ESP32 DevKit V1 (ESP-WROOM-32, 30 ขา, ชิป CP2102) เชื่อมต่อ Wi-Fi ภายในวง LAN
  - ตัวขับแขนไม้กั้นจำลอง: เซอร์โวมอเตอร์ TowerPro SG90 ยกแขนไม้กั้นจำลอง 0-90 องศา
  - ระบบความปลอดภัย (Safety Interlock & Auto-Close): เซนเซอร์อัลตราโซนิก HC-SR04 วัดระยะสิ่งกีดขวางบริเวณใต้ไม้กั้น ป้องกันไม้กั้นปิดลงมาตีคนหรือรถจำลอง และสั่งปิดอัตโนมัติเมื่อผ่านพ้นไปแล้ว
  - ส่วนแสดงผลและเสียงแจ้งเตือนหน้าป้อมยาม: จอ LCD 16x2 (1602A) พร้อมโมดูล I2C + ชุดไฟแสดงสถานะ LED (สีเขียว/สีแดง) + ลำโพง Piezo Buzzer แจ้งเตือนสถานะผ่าน-ไม่ผ่าน


3. กระบวนการอนุมัติและกติกาการผูกสายอนุมัติอัตโนมัติ 5 ขั้นตอน (5-Tier Routing Logic)
--------------------------------------------------------------------------------
คำร้องขออนุญาตต้องผ่านการพิจารณาตามลำดับขั้นอย่างเคร่งครัด โดยมีกลไกผูกหาผู้อนุมัติอัตโนมัติจากข้อมูลตั้งต้นของแผนกเทคโนโลยีธุรกิจดิจิทัล ดังนี้:

  ขั้นที่ 1: ครูรายวิชา (Subject Teacher)
           - กลไกการผูกสายอนุมัติ: ดึงข้อมูลอัตโนมัติจากตารางเรียน (courses_schedule) ของห้องเรียนนักเรียนในคาบเวลานั้น หรือให้นักเรียนกดเลือกวิชาจากรายการวิชาที่มีข้อมูลตั้งต้นไว้อยู่แล้ว ระบบจะผูกหาครูประจำวิชานั้นทันที
           - หน้าที่ตรวจสอบ: ตรวจสอบว่านักเรียนมีเรียนหรือมีการสอบในคาบเวลาที่ขอออกหรือไม่

  ขั้นที่ 2: ครูที่ปรึกษา (Advisor Teacher)
           - กลไกการผูกสายอนุมัติ: ระบบดึงชื่อครูที่ปรึกษาอัตโนมัติจากกลุ่มเรียน (class_groups.advisor_teacher_id) ที่นักเรียนสังกัด
           - หน้าที่ตรวจสอบ: ตรวจสอบความจำเป็น พฤติกรรม และประสานงานยืนยันกับผู้ปกครอง

  ขั้นที่ 3: หัวหน้าแผนก (Department Head)
           - กลไกการผูกสายอนุมัติ: ระบบดึงชื่อหัวหน้าแผนกเทคโนโลยีธุรกิจดิจิทัลอัตโนมัติ (departments.head_teacher_id)
           - หน้าที่ตรวจสอบ: กลั่นกรองความเหมาะสมระดับแผนกวิชา

  ขั้นที่ 4: ฝ่ายปกครอง / กิจการนักเรียน (Discipline Officer)
           - กลไกการผูกสายอนุมัติ: ส่งเข้าคิวกลางของกลุ่มผู้ใช้บทบาท discipline (เจ้าหน้าที่ฝ่ายปกครองท่านใดกดอนุมัติก่อนก็ได้ เพื่อลดปัญหาคอขวด)
           - หน้าที่ตรวจสอบ: ตรวจสอบประวัติการขอออกนอกสถานศึกษาและระเบียบวินัย

  ขั้นที่ 5: รองผู้อำนวยการ (Deputy Director)
           - กลไกการผูกสายอนุมัติ: ส่งเข้าคิวกลางของกลุ่มผู้ใช้บทบาท deputy_director (ท่านใดกดอนุมัติก่อนก็ได้) เพื่อพิจารณาอนุมัติขั้นสุดท้าย (Final Sign-off)

* เงื่อนไข Time-Window (การจำกัดช่วงเวลา):
  - ทุกคำร้องต้องระบุ "ช่วงเวลาที่อนุญาตให้ออก" (เช่น 12:30 - 14:30 น.)
  - ระบบจะส่งสิทธิ์เข้า Local Whitelist เฉพาะเมื่ออนุมัติครบ 5 ขั้นตอนและอยู่ในช่วงเวลานั้นเท่านั้น หากพ้นกำหนดแล้วยังไม่ได้สแกนออก สิทธิ์จะเปลี่ยนสถานะเป็นหมดอายุ (Expired) ทันที


4. ขอบเขตงานรายโมดูล (Scope of Work / Modules)
--------------------------------------------------------------------------------
[โมดูลที่ 1] ระบบเว็บแอปพลิเคชัน (PWA) และการแจ้งเตือน
  - พัฒนาระบบยืนยันตัวตน (รหัสนักศึกษา/บุคลากร + Face ID ผ่านเว็บแคม) และจัดการสิทธิ์ผู้ใช้งาน (RBAC) ครบทุกบทบาท (student, subject_teacher, advisor, dept_head, discipline, deputy_director, guard, admin)
  - ระบบลงทะเบียนใบหน้านักเรียน (Face Enrollment / Re-enroll Face): เปิดกล้องเว็บแคมถ่ายภาพหน้าตรงหรืออัปโหลดภาพเพื่อสกัดเป็น Face Embeddings
  - รองรับการทำงานแบบ PWA และส่ง Web Push Notification / แจ้งเตือนผู้ปกครองเมื่อผ่านไม้กั้น

[โมดูลที่ 2] ระบบจัดการการอนุมัติ 5 ขั้นตอน (Workflow Engine)
  - ออกแบบ State Machine รองรับการส่งต่อคำขอทีละขั้น (Step 1 -> 2 -> 3 -> 4 -> 5) และการตีกลับ/ปฏิเสธพร้อมระบุเหตุผล
  - ระบบ Proxy / Delegate Approval: สามารถตั้งค่าผู้รักษาการแทนกรณีผู้อนุมัติหลักติดภารกิจ เพื่อลดปัญหาคอขวด
  - ระบบจัดการ Time-Window และ Expiration อัตโนมัติ พร้อมบันทึกเวลารายงานตัวกลับเข้าวิทยาลัย

[โมดูลที่ 3] ระบบ AI จดจำใบหน้า (Local Edge AI Face Recognition ผ่านกล้องเว็บแคม)
  - รับภาพจากกล้อง Webcam แบบ Real-time (30 FPS) ผ่าน WebRTC / OpenCV เพื่อสกัดตำแหน่งใบหน้า (RetinaFace / SCRFD) และค่าคุณลักษณะใบหน้า (InsightFace / ArcFace)
  - ระบบ Anti-Spoofing (Liveness Detection) ป้องกันการนำภาพถ่ายหรือหน้าจอมือถือมาหลอกกล้องเว็บแคม
  - ระบบ Local Whitelist Sync & Cache: ซิงค์ข้อมูลอัตโนมัติจาก Web Backend และเปรียบเทียบใบหน้ากับ Local Whitelist Cache ด้วยความเร็ว < 0.5 วินาที พร้อมทำงานแบบ Offline Resilient (เปิดไม้กั้นได้แม้เน็ตนอกหลุด)

[โมดูลที่ 4] ระบบ IoT ควบคุมไม้กั้น (Hardware & Gate Controller)
  - พัฒนาเฟิร์มแวร์บน ESP32 รับคำสั่งเปิดไม้กั้นจาก Local PC ผ่าน Local HTTP REST API หรือ Local MQTT
  - ควบคุม Relay Module / มอเตอร์ไม้กั้นจำลอง ด้วยสัญญาณแบบ Pulse (เช่น ทริกเกอร์ 0.5 วินาที) หรือควบคุม Servo ยกแขนกั้นจำลองตามสเปกอุปกรณ์จริง
  - เชื่อมโยง Safety Sensor เพื่อควบคุมจังหวะปิดไม้กั้นอย่างปลอดภัย

[โมดูลที่ 5] ระบบตรวจสอบหน้าประตูและรายงาน (Guard Monitor & Audit Trail)
  - หน้าจอมอนิเตอร์ Real-time สำหรับ รปภ.: แสดงภาพสดจากกล้องเว็บแคม, กรอบตรวจจับใบหน้า, ข้อมูลนักเรียนที่อนุมัติเทียบกับภาพต้นฉบับ
  - ปุ่ม Emergency Manual Release สำหรับ รปภ. กดเปิดไม้กั้นกรณีฉุกเฉิน
  - ระบบบันทึกประวัติการออก (Exit Logs): เก็บเวลาที่ออกจริงและเวลากลับเข้าวิทยาลัย พร้อมภาพ Snapshot จากเว็บแคม ณ จังหวะที่ผ่านประตู เพื่อทำรายงานและตรวจสอบย้อนหลัง


5. ประเด็นความท้าทายทางเทคนิคและแนวทางป้องกัน (Key Considerations)
--------------------------------------------------------------------------------
1. การลดคอขวดของขั้นตอนการอนุมัติ 5 ระดับ:
   - ปัญหา: หากครูหรือผู้บริหารในขั้นใดขั้นหนึ่งติดสอนหรือประชุม คำร้องอาจค้างนานเกินช่วงเวลาที่ขอออก
   - แนวทางป้องกัน: พัฒนาระบบผู้รักษาการแทน (Delegate/Proxy Approval) ส่งเข้าคิวกลางในขั้นที่ 4-5 และแจ้งเตือนด่วน (High-Priority Alert)
2. สภาพแสงและการติดตั้งกล้องเว็บแคม (Webcam Placement & Lighting):
   - ปัญหา: แสงย้อนหลังหรือแสงน้อยในจุดตั้งชุดจำลองอาจทำให้กล้องเว็บแคมตรวจจับใบหน้าพลาดหรือใช้เวลานาน
   - แนวทางป้องกัน: วางตำแหน่งกล้องเว็บแคมให้อยู่ในระดับสายตาบนโต๊ะจุดสาธิต หันหน้ากล้องหลีกเลี่ยงแสงย้อนจากหน้าต่าง/ประตู และเตรียมไฟส่องสว่างเสริม (LED Ring Light หรือไฟตั้งโต๊ะ) ให้เห็นใบหน้าชัดเจน
3. ความปลอดภัยของระบบไม้กั้นอัตโนมัติ:
   - ปัญหา: สัญญาณค้างหรือไม้กั้นตีลงมาโดนผู้ใช้งาน/รถ
   - แนวทางป้องกัน: ใช้การสั่งงานแบบ Pulse Signal / State Guard และมี Safety Sensor ป้องกันไม้กั้นปิดทับสิ่งกีดขวาง


6. โครงสร้างฐานข้อมูลหลัก (Database Schema - 7 ตารางหลัก)
--------------------------------------------------------------------------------
ออกแบบรองรับข้อมูลตั้งต้นของแผนกเทคโนโลยีธุรกิจดิจิทัล การอนุมัติ 5 ขั้นตอน และระบบสแกนใบหน้า:

  [ตารางที่ 1] departments (แผนกวิชา)
    - id (PK), code (เช่น 'DBT'), name (ตั้งต้น: 'เทคโนโลยีธุรกิจดิจิทัล')
    - head_teacher_id (FK -> users.id) : ผูกหัวหน้าแผนกเพื่อส่งอนุมัติขั้นที่ 3 อัตโนมัติ

  [ตารางที่ 2] class_groups (ห้องเรียน / กลุ่มเรียน)
    - id (PK), department_id (FK -> departments.id)
    - group_code (เช่น 'ปวช.3/1', 'ปวส.2/1'), level ('ปวช.' / 'ปวส.')
    - advisor_teacher_id (FK -> users.id) : ผูกครูที่ปรึกษาเพื่อส่งอนุมัติขั้นที่ 2 อัตโนมัติ

  [ตารางที่ 3] users (ผู้ใช้งานทุกบทบาท)
    - id (PK), username / student_or_staff_code, password_hash, full_name
    - role (ENUM: 'student', 'subject_teacher', 'advisor', 'dept_head', 'discipline', 'deputy_director', 'guard', 'admin')
    - class_group_id (FK -> class_groups.id, nullable สำหรับบุคลากร)
    - department_id (FK -> departments.id, nullable สำหรับฝ่ายกลาง)
    - phone, email, push_subscription (JSON สำหรับ Web Push Notification), is_active
    - pdpa_consented (BOOLEAN ยืนยันรับทราบนโยบาย PDPA แล้วหรือไม่), pdpa_consented_at (TIMESTAMP)

  [ตารางที่ 4] courses_schedule (ข้อมูลรายวิชาและตารางสอนตั้งต้นของแผนก ทธด.)
    - id (PK), course_code, course_name
    - class_group_id (FK -> class_groups.id)
    - teacher_id (FK -> users.id) : ครูประจำวิชาสำหรับขั้นที่ 1
    - day_of_week (1-7), start_time, end_time

  [ตารางที่ 5] face_embeddings (ข้อมูลคุณลักษณะใบหน้านักเรียนสำหรับ AI)
    - id (PK), user_id (FK -> users.id)
    - embedding_vector (Array/Vector 512 มิติ หรือ JSON/BLOB)
    - sample_image_path (รูปภาพต้นฉบับสำหรับแสดงเทียบหน้าจอ รปภ.)
    - is_active, created_at

  [ตารางที่ 6] leave_requests (ใบคำร้องขออนุญาตออกนอกสถานศึกษา)
    - id (PK), request_code (เลขที่ใบคำร้อง รูปแบบ #GP-2569-XXX)
    - student_id (FK -> users.id)
    - course_id (FK -> courses_schedule.id, nullable กรณีไม่ได้ขอลาในคาบเรียน)
    - category (ENUM: 'medical', 'personal', 'department', 'parent_pickup')
    - reason (เหตุผลที่ขอออก), destination_name (ชื่อสถานที่ปลายทางที่แจ้ง), destination_lat (REAL), destination_lng (REAL พิกัดปลายทางที่นักศึกษาเลื่อนหมุดยืนยันบนแผนที่ในแชท), attachment_path (ไฟล์แนบ เช่น ใบนัดแพทย์), leave_date, allowed_start_time, allowed_end_time
    - ข้อมูลตรวจสอบพิกัด GPS และรูปถ่ายสดในโหมด Live Trip:
      * checkin_lat, checkin_lng, checkin_at, checkin_distance_m (ระยะห่างจากพิกัดปลายทางเป็นเมตร คำนวณด้วยสูตร Haversine), checkin_verified (BOOLEAN ยืนยันว่าไปถึงสถานที่ที่แจ้งจริง)
      * dest_checkin_photo_path (รูปถ่ายสดจากกล้อง ณ สถานที่ปลายทางตอนกดเช็คอินถึงจุดหมาย)
      * return_checkin_photo_path (รูปถ่ายสดจากกล้องตอนรายงานตัวกลับถึงวิทยาลัย)
      * is_return_required (BOOLEAN 1=ต้องกลับ, 0=ออกยาว/ไม่กลับ)
      * trip_stage (ENUM: 'not_started', 'heading_to_dest', 'at_dest', 'heading_back', 'completed')
      * dest_arrived_at, return_arrived_at, current_lat, current_lng
    - current_step (TINYINT 1..5), overall_status (ENUM: 'pending', 'approved', 'rejected', 'completed_exit', 'returned', 'expired')
    - การบันทึกผลทั้ง 5 ขั้นตอน:
      * step1_teacher_id, step1_status, step1_remark, step1_acted_at
      * step2_advisor_id, step2_status, step2_remark, step2_acted_at
      * step3_dept_head_id, step3_status, step3_remark, step3_acted_at
      * step4_discipline_id, step4_status, step4_remark, step4_acted_at
      * step5_deputy_id, step5_status, step5_remark, step5_acted_at
    - synced_to_gate (BOOLEAN), created_at, updated_at

  [ตารางที่ 7] gate_exit_logs (ประวัติการสแกนหน้าเปิดไม้กั้นหน้าประตู)
    - id (PK), request_id (FK -> leave_requests.id, nullable กรณี Manual Release)
    - student_id (FK -> users.id, nullable)
    - direction (ENUM: 'exit', 'return') : บันทึกทั้งขาออกและขากลับรายงานตัว
    - gps_lat, gps_lng (พิกัด GPS ขณะสแกนออกและรายงานตัวกลับเข้าวิทยาลัย)
    - similarity_score (FLOAT ค่าความคล้ายของใบหน้าจาก AI)
    - snapshot_image_path (ภาพถ่ายจังหวะเดินผ่านไม้กั้น)
    - trigger_type (ENUM: 'ai_auto', 'guard_manual')
    - triggered_by_guard_id (FK -> users.id, nullable)
    - gate_opened_at (TIMESTAMP)

8. สเปกการเชื่อมต่อ API (API Contract: Web <-> Local AI <-> ESP32/Simulator)
--------------------------------------------------------------------------------
กำหนด API Endpoints หลักเพื่อเชื่อมโยงข้อมูลทั้ง 3 ส่วนเข้าด้วยกันอย่างเป็นระบบ:

  1. POST /api/requests
     - หน้าที่: นักเรียนยื่นคำร้องขออนุญาตออกนอกสถานศึกษา (ระบบผูกสายอนุมัติ 5 ขั้นตอนอัตโนมัติจากวิชา/ห้องเรียน/แผนก)

  2. POST /api/requests/{id}/approve
     - หน้าที่: ผู้อนุมัติลำดับที่ 1-5 กดอนุมัติหรือปฏิเสธ พร้อมบันทึกหมายเหตุและอัปเดต current_step

  3. GET /api/gate/whitelist
     - หน้าที่: Local AI Service ดึงรายชื่อนักเรียนที่อนุมัติครบ 5 ขั้นตอน (overall_status = 'approved') และอยู่ในช่วงเวลา (allowed_start_time ถึง allowed_end_time) พร้อม embedding_vector มาแคชไว้

  4. POST /api/gate/verify-face
     - หน้าที่: ประมวลผลเปรียบเทียบใบหน้าจากกล้องเว็บแคมกับ Whitelist และตรวจสอบสิทธิ์ช่วงเวลา

  5. POST http://<esp32-ip-or-simulator>/gate/open
     - หน้าที่: ส่งสัญญาณ Pulse 0.5 วินาทีสั่งเปิดไม้กั้น (ใช้ Endpoint รูปแบบเดียวกันทั้งกับ Virtual Gate Simulator และบอร์ด ESP32 จริง)

  6. POST /api/gate/logs
     - หน้าที่: บันทึกเวลาออกจริง/ขากลับรายงานตัว พิกัด GPS และภาพถ่าย Snapshot จากเว็บแคมลงตาราง gate_exit_logs พร้อมอัปเดตสถานะใบคำร้อง (completed_exit / returned)

  7. POST /api/users/pdpa-consent
     - หน้าที่: บันทึกการกดยินยอม PDPA ของนักศึกษา (ครอบคลุมการจัดเก็บข้อมูลชีวมิติใบหน้า AI และพิกัด GPS เฉพาะช่วงเวลาที่ขออนุญาต)

  8. POST /api/requests/{id}/checkin-gps
     - หน้าที่: รับค่าพิกัด lat, lng เมื่อนักศึกษากดปุ่ม [📍 เช็คอินถึงจุดหมาย] ในแชท คำนวณระยะทางเทียบกับสถานที่ปลายทางที่แจ้งไว้ (Haversine) และสร้างลิงก์ Google Maps ให้ครูที่ปรึกษา/งานปกครองตรวจสอบ


9. การออกแบบหน้าจอ UX/UI ตามไฟล์ต้นแบบ (โฟลเดอร์ UI/) และส่วนขยายระบบ
--------------------------------------------------------------------------------
ออกแบบหน้าจอ Mobile-First PWA ให้ตรงตามไฟล์ภาพต้นแบบใน C:\Users\com\Desktop\GSF\UI\ ทั้ง 4 หน้าจอ และผสานเข้ากับ Workflow 5 ขั้นตอน ดังนี้:

  - แถบเมนูนำทางด้านล่าง (Bottom Navigation 4 แท็บ): [หน้าแรก] | [แชทขออนุญาต] | [สแกนไม้กั้น] | [โปรไฟล์]
  - ฟีเจอร์พิเศษสำหรับโปรเจกต์จบ (Quick Demo Role Switcher): แถบสลับบทบาทด่วน (นักเรียน -> ครูรายวิชา -> ครูที่ปรึกษา -> หัวหน้าแผนก ทธด. -> ฝ่ายปกครอง -> รอง ผอ. -> รปภ.) เพื่อใช้สาธิตให้กรรมการดูได้ครบทุกขั้นตอนในเครื่องเดียว

[9.2] หน้าจอที่ 1: เข้าสู่ระบบ / ลงทะเบียนใบหน้า (อ้างอิง UI/screen-1-login.png)
  - ส่วนหัว: โลโก้ Smart Gate Pass AI พร้อมป้าย AI FACE, ชื่อ "วิทยาลัยการอาชีพองครักษ์ (OICEC)" และคำอธิบายระบบ
  - แท็บสลับโหมดด้านบนการ์ด: [เข้าสู่ระบบ] | [ลงทะเบียนใบหน้า] (เปิดหน้าต่างกล้อง Webcam เพื่อเก็บภาพใบหน้า 3-5 มุมสำหรับลงทะเบียน AI)
  - หน้าต่างและช่องติ๊กยินยอม PDPA (PDPA Consent Modal & Checkbox): แสดงก่อนลงทะเบียนใบหน้าหรือเข้าสู่ระบบครั้งแรก โดยแจ้งวัตถุประสงค์ชัดเจนว่าจัดเก็บข้อมูลชีวมิติใบหน้า AI และตรวจสอบพิกัด GPS เฉพาะช่วงเวลาที่ขออนุญาตออกนอกวิทยาลัยการอาชีพองครักษ์เท่านั้น (ไม่ติดตามนอกเวลา)
  - ฟอร์มเข้าสู่ระบบ: ช่องกรอก "รหัสนักศึกษา / บุคลากร" และ "รหัสผ่าน" พร้อมปุ่มหลัก "เข้าสู่ระบบขออนุญาต ->" และปุ่มรอง "สแกนใบหน้าเพื่อเข้าสู่ระบบ (Face ID)" (เปิดกล้อง Webcam ยืนยันตัวตน)
  - ส่วนเชื่อมโยงระบบสถานศึกษาด้านล่าง: ปุ่ม "ระบบ ศธ.02" และ "แจ้งผู้ปกครอง" (LINE) รวมถึงข้อความเครดิต "งานปกครอง วก.องครักษ์"

[9.3] หน้าจอที่ 2: หน้าแรก Dashboard (อ้างอิง UI/screen-2-home.png)

14. รายการอุปกรณ์ฮาร์ดแวร์ชุดจำลองและแผนการต่อวงจร (Confirmed IoT Hardware & Pinout Plan - ครบทั้ง 7 ชิ้น)

[14.1] อุปกรณ์ที่ยืนยันแล้วครบชุด (อ้างอิงภาพอุปกรณ์จริงในโฟลเดอร์ IOT/ และรายการเสริม):
  1) บอร์ดไมโครคอนโทรลเลอร์ (IOT/ESP32-chip.webp):
     - รุ่น: ESP32 DevKit V1 (โมดูล ESP-WROOM-32, 30 ขา, ชิปแปลงพอร์ต CP2102 Micro-USB)
     - หน้าที่: เชื่อมต่อ Wi-Fi ภายในวง LAN รอรับคำสั่ง HTTP /api/gate/open จากคอมพิวเตอร์ และสั่งงานอุปกรณ์ทั้งหมดหน้าไม้กั้น

  2) กล้องเว็บแคม (IOT/images.jpg):
     - รุ่น: USB Webcam Full HD (ต่อสาย USB เข้าคอมพิวเตอร์/โน้ตบุ๊กโดยตรง)
     - หน้าที่: สแกนใบหน้า AI ครบทั้ง 3 จุด ได้แก่ ลงทะเบียนใบหน้า, Face ID Login และสแกนเปิดไม้กั้นหน้าป้อมยามประตู 1

  3) เซอร์โวมอเตอร์ยกไม้กั้น (IOT/images (2).jpg):
     - รุ่น: TowerPro Micro Servo 9g (SG90) 3 สาย (น้ำตาล=GND, แดง=VCC, ส้ม=PWM Signal)
     - หน้าที่: ขับแขนไม้กั้นจำลอง (หมุน 0 องศา = ปิดไม้กั้น, 90 องศา = เปิดไม้กั้น)
     - การต่อขา ESP32: น้ำตาล -> GND | แดง -> 5V / VIN | ส้ม -> GPIO 13

  4) เซนเซอร์วัดระยะป้องกันไม้กั้นตี (IOT/images (1).jpg):
     - รุ่น: Ultrasonic Distance Sensor HC-SR04 (4 ขา: VCC, Trig, Echo, GND)
     - หน้าที่ (Safety Interlock & Auto-Close): วัดระยะสิ่งกีดขวางบริเวณจุดผ่านไม้กั้น (< 10 ซม. ล็อกไม้กั้นไม่ให้ปิดลงมาตี / > 15 ซม. ต่อเนื่อง 3 วินาที สั่งพับไม้กั้นลงอัตโนมัติ)
     - การต่อขา ESP32: VCC -> 5V / VIN | GND -> GND | Trig -> GPIO 5 | Echo -> GPIO 18 (แนะนำต่อตัวต้านทานแบ่งแรงดัน 5V->3.3V เข้าขา Echo เพื่อถนอมบอร์ด)

  5) จอแสดงผลสถานะหน้าป้อมยาม (IOT/c51p4i.jpg):
     - รุ่น: จอ LCD 16x2 (1602A) พร้อมโมดูลแปลงสัญญาณ I2C ด้านหลัง (4 ขา: GND, VCC, SDA, SCL)
     - หน้าที่: แสดงข้อความสถานะหน้าประตู เช่น ชื่อนักศึกษา, เลขที่ใบอนุญาต #GP-2569-XXX, "PASS / GATE OPEN" หรือ "ACCESS DENIED"
     - การต่อขา ESP32: GND -> GND | VCC -> 5V / VIN | SDA -> GPIO 21 | SCL -> GPIO 22

  6) ลำโพงเสียงแจ้งเตือน (IOT/5t94v5.png):
     - รุ่น: Piezo Buzzer (บัซเซอร์ 2 ขา)
     - หน้าที่: ส่งเสียงบี๊บ 1 ครั้งเมื่อสแกนผ่านและไม้กั้นเปิด / ส่งเสียงเตือนรัวเมื่อไม่มีสิทธิ์ผ่าน
     - การต่อขา ESP32: ขาบวก (+) -> GPIO 19 | ขาลบ (-) -> GND

  7) ชุดไฟแสดงสถานะหน้าไม้กั้น (LED Status Indicator - ไม่มีไฟล์ภาพในโฟลเดอร์ IOT/ แต่ยืนยันใช้งานในชุดจำลอง):
     - หน้าที่: แสดงสถานะไฟสัญญาณหน้าไม้กั้นจำลองควบคู่กับจอ LCD และเสียง Buzzer:
       * ไฟสีแดง (Red LED): ติดค้างในสถานะปกติ (ไม้กั้นปิด) หรือกะพริบเตือนเมื่อสแกนใบหน้าไม่ผ่าน / ไม่มีสิทธิ์ออก
       * ไฟสีเขียว (Green LED): ติดสว่างเมื่อสแกนใบหน้าผ่านและแขนไม้กั้นเปิดให้เดินผ่าน (ดับลงและสลับกลับเป็นสีแดงเมื่อไม้กั้นปิด)
     - การจองขาพินบนบอร์ด ESP32 DevKit V1 (30 ขา):
       * ไฟ LED สีเขียว (+) -> ต่อขา GPIO 25 (ผ่านตัวต้านทาน 220 โอห์ม ลง GND หรือต่อเข้าขาโมดูล LED)
       * ไฟ LED สีแดง (+)   -> ต่อขา GPIO 26 (ผ่านตัวต้านทาน 220 โอห์ม ลง GND หรือต่อเข้าขาโมดูล LED)
       * (สำรองขา GPIO 27 กรณีเป็นโมดูลไฟจราจร 3 สี แดง-เหลือง-เขียว หรือไฟส่องสว่างเสริม)

[14.2] ข้อควรระวังในการต่อวงจรชุดจำลอง (ขนาดฐาน 60 x 60 x 10 ซม.):
  - เนื่องจาก SG90, จอ LCD 16x2 และ HC-SR04 ใช้ไฟเลี้ยง 5V ควรจ่ายไฟเลี้ยงบอร์ดผ่านสาย Micro-USB 5V คุณภาพดี (หรือรางไฟ 5V แยกพร้อม Ground ร่วมกัน) เพื่อป้องกันอาการบอร์ด ESP32 รีเซ็ตเมื่อ Servo เริ่มหมุน

[15.1] โครงสร้างเนื้อหาบทที่ 3 วิธีดำเนินการโครงงาน (ตามมาตรฐาน วก.องครักษ์ / สอศ. และข้อมูลจริงในระบบ):

  3.1 ประชากรและกลุ่มตัวอย่าง
      - กลุ่มตัวอย่างจำนวนทั้งสิ้น 22 คน ประกอบด้วย นักศึกษาสาขางานเทคโนโลยีธุรกิจดิจิทัล วิทยาลัยการอาชีพองครักษ์ จำนวน 20 คน และครูผู้สอน จำนวน 2 คน (เลือกแบบเจาะจง: Purposive Sampling)

  3.2 เครื่องมือ วัสดุอุปกรณ์ และซอฟต์แวร์ที่ใช้ในการจัดทำโครงงาน
      - ตารางที่ 3.1 รายการวัสดุอุปกรณ์ฮาร์ดแวร์ชุดจำลองไม้กั้น (ฐานขนาด 60 x 60 x 10 ซม.) ครบทั้ง 7 ชิ้น:
        1) บอร์ดไมโครคอนโทรลเลอร์ ESP32 DevKit V1 (ESP-WROOM-32, 30 ขา, CP2102)
        2) กล้องเว็บแคมความละเอียดสูง USB Webcam Full HD
        3) เซอร์โวมอเตอร์ TowerPro SG90 (ควบคุมมุม 0-90 องศา)
        4) เซนเซอร์วัดระยะอัลตราโซนิก HC-SR04 (Safety Interlock กันไม้กั้นตี + Auto-Close)
        5) จอแสดงผล LCD 16x2 (1602A) พร้อมโมดูล I2C
        6) ลำโพงแจ้งเตือน Piezo Buzzer (2 ขา)
        7) ชุดไฟแสดงสถานะ LED สีเขียว/แดง หน้าไม้กั้น
      - ตารางที่ 3.2 รายการซอฟต์แวร์และเทคโนโลยีที่ใช้พัฒนา:
        * Next.js (App Router, TypeScript, Tailwind CSS) แบบ Progressive Web App (PWA)
        * ฐานข้อมูล SQLite 7 ตารางหลัก (web-app/src/lib/schema.sql)
        * Google Gemini AI Chatbot (ระบบ Slot-Filling + Fallback ภาษาไทยธรรมชาติ)
        * WebRTC & AI Face Recognition (สแกนใบหน้าลงทะเบียน, Face ID, และเปิดไม้กั้น)
        * Web Geolocation API (GPS Check-in ปลายทาง/รัศมีวิทยาลัย) & PDPA Consent
        * Arduino IDE สำหรับเขียนและอัปโหลดเฟิร์มแวร์ควบคุมบอร์ด ESP32 (iot-esp32/)

  3.3 การออกแบบและขั้นตอนการพัฒนาระบบ
      - 3.3.1 การออกแบบสถาปัตยกรรมระบบและแผนภาพการทำงานรวม (System Architecture Flowchart)
      - 3.3.2 การออกแบบระบบแชทบอท AI (Slot-Filling: เก็บสถานที่ปลายทาง, เหตุผล, เวลาออก-กลับ, เอกสาร/รูปแชทผู้ปกครองแบบไม่บังคับ) และผังงานการอนุมัติ 5 ขั้นตอนอัตโนมัติตามตารางเรียนจริง 5 ชั้นปี (timetable/)
      - 3.3.3 การออกแบบฐานข้อมูลเชิงสัมพันธ์ 7 ตารางหลัก (ER Diagram และตาราง Data Dictionary ทั้ง 7 ตารางจาก web-app/src/lib/schema.sql)
      - 3.3.4 การออกแบบส่วนติดต่อผู้ใช้งาน (User Interface) ครบทุกหน้าจอจริงใน web-app/ (login, home, chat, profile, approver, gate, และ admin/database)
      - 3.3.5 การออกแบบวงจรและการเชื่อมต่อพินบอร์ดไมโครคอนโทรลเลอร์ ESP32 (SG90 -> GPIO 13, HC-SR04 -> GPIO 5/18, LCD I2C -> GPIO 21/22, Buzzer -> GPIO 19, LED เขียว/แดง -> GPIO 25/26)

  3.4 เครื่องมือที่ใช้ในการเก็บรวบรวมข้อมูลและการหาประสิทธิภาพ
      - 3.4.1 แบบบันทึกผลการทดสอบประสิทธิภาพของระบบ (ความถูกต้องของการรับคำขอผ่านแชท AI, การส่งต่ออนุมัติ 5 ขั้นตอน, การเช็คอินพิกัด GPS, และความแม่นยำในการสแกนใบหน้าเปิดไม้กั้น)
      - 3.4.2 แบบสอบถามความพึงพอใจของผู้ใช้งาน (มาตราส่วนประมาณค่า 5 ระดับ Likert Scale ครอบคลุม 3 ด้านหลัก: ด้านการใช้งานและออกแบบระบบ, ด้านความถูกต้องแม่นยำและรวดเร็ว, และด้านความปลอดภัยและความเหมาะสมในการใช้งานจริง)

  3.5 การเก็บรวบรวมข้อมูลและสถิติที่ใช้ในการวิเคราะห์ข้อมูล
      - ขั้นตอนการทดลองใช้จริงกับกลุ่มตัวอย่าง 22 คน
      - สถิติที่ใช้ (Word Equation OMML): สมการค่าร้อยละ (P), ค่าเฉลี่ยเลขคณิต (x-bar), ส่วนเบี่ยงเบนมาตรฐาน (S.D.) และเกณฑ์การแปลความหมาย 5 ระดับ (เกณฑ์สมมติฐานค่าเฉลี่ย >= 3.51)

[15.2] รายการบรรณานุกรมงานวิจัยจริงทั้ง 5 เรื่องจากฐานข้อมูล TCI-ThaiJO (สำหรับใช้อ้างอิงในบทที่ 2, บทที่ 5 และบรรณานุกรมท้ายเล่ม):
  1) ธนพล แก้วคำแจ้ง, ประวิทย์ บุรินนิตย์, กัมปนาท บุญคง, ณัฐพล บูระนะเวช และธีรพัฒน์ เสมเหลา. (2567). การศึกษาและประยุกต์ใช้งาน ESP32 จำลองประตูอัจฉริยะตรวจจับใบหน้าเพื่อความปลอดภัย. วารสารวิจัยและนวัตกรรมการอาชีวศึกษา (สาขาวิชาเทคโนโลยีอิเล็กทรอนิกส์ วิทยาลัยเทคนิคหนองบัวลำภู สถาบันอาชีวศึกษาภาคตะวันออกเฉียงเหนือ; ฐานข้อมูล TCI-ThaiJO).
  2) วุฒิชัย เหล่าสียง และทรงลักษณ์ สกุลวิจิตร์สินธุ. (2566). การพัฒนาระบบสารสนเทศเพื่องานส่งเสริมบริหารกิจการนักเรียน โรงเรียนวัดธรรมจริยาภิรมย์ จังหวัดสมุทรสาคร. วารสารวิจัย สมาคมห้องสมุดแห่งประเทศไทยฯ, ปีที่ 16 ฉบับที่ 1 (มกราคม–มิถุนายน 2566) (มหาวิทยาลัยสุโขทัยธรรมาธิราช; ฐานข้อมูล TCI-ThaiJO).
  3) พิศณุ คูมีชัย. (2565). เทคโนโลยีการรู้จำใบหน้ามนุษย์ด้วยการประมวลผลภาพ. วารสารวิชาการโรงเรียนนายเรือ ด้านวิทยาศาสตร์และเทคโนโลยี, ปีที่ 5 ฉบับที่ 1 (พ.ศ. 2565) (ฐานข้อมูล TCI-ThaiJO).
  4) ธนพร พยอมใหม่, วิญญู ศิลาบุตร, ไมตรี ธรรมมา, วิชชุพงษ์ วิบูลเจริญ และสมสิน วางขุนทด. (2564). ระบบสมองกลฝังตัวสำหรับการควบคุมประตูอัตโนมัติด้วยใบหน้า. วารสารวิทยาศาสตร์และเทคโนโลยี หัวเฉียวเฉลิมพระเกียรติ (มหาวิทยาลัยเทคโนโลยีราชมงคลอีสาน นครราชสีมา; ฐานข้อมูล TCI-ThaiJO).
  5) ธนภัทร กุหลาบทิพย์ และคงวุฒิ แสงกล้า. (2561). การพัฒนาระบบลางานออนไลน์ของสหกรณ์ออมทรัพย์ขอนแก่น จำกัด. วารสารวิทยาศาสตร์และเทคโนโลยี มหาวิทยาลัยราชภัฏมหาสารคาม, ปีที่ 1 ฉบับที่ 2 (กรกฎาคม–ธันวาคม พ.ศ. 2561) (ฐานข้อมูล TCI-ThaiJO).
